# CFO Multi-Agents 协同研究方法论

**版本**：v2.5
**适用范围**：多专业协同研究、方案制定、尽调报告等需拆解为并行子任务的项目
**前置条件**：已配置Team各角色

---

## 1. 适用场景

本方法论适用于以下类型项目：

- 需要多个专业领域Agent并行研究的复杂课题（如IPO流程、并购方案、税务筹划等）
- 产出物为多份专业报告 + 一份合稿的一对多文档结构
- 对数据准确性和跨专业一致性要求较高
- 主Agent无法独立覆盖全部专业领域

不适用的场景：
- 单一领域的简单问答
- 纯代码编写或调试任务
- 不需要跨专业交叉验证的信息检索

## 2. 团队配置

### 2.1 角色分工

| 角色 | 职责 | 说明 |
|:---|:---|:---|
| **主控Agent** | 任务拆解、调度协调、流程把控、最终合稿 | 唯一的流程Owner，不直接参与专业研究 |
| **专业Agent × N** | 各自领域的独立研究、交叉审核、辩论、按意见修改 | N取决于项目涉及的专业领域数 |
| **COO（内部运营管理）** | 组织落地评估、激励方案设计、变革管理、员工沟通、**案例对标与最佳实践借鉴** | 企业内部视角，从"能不能落地"审视所有外部方案，同时研究同行案例寻找可借鉴经验 |
| **编辑** | 三轮质量审核（格式+逻辑+数据一致性+引用标注） | 独立于专业Agent，直接向主控汇报 |

**COO角色的适用场景**：

| 场景 | 参与程度 | 价值点 |
|:---|:---:|:---|
| ESOP/股权激励方案 | 🔴 深度参与 | 激励方案设计、授予分层、绩效挂钩、员工沟通、离职管理 |
| 红筹搭建/拆除方案 | 🟡 中等参与 | 人员架构梳理、股权代持还原、组织过渡方案 |
| IPO方案 | 🟡 中等参与 | 组织准备度评估、内控流程、员工沟通 |
| 并购/重组方案 | 🟡 中等参与 | 整合方案、文化融合、人才保留 |
| 投融资方案 | 🟢 轻度参与 | 管理团队评估、组织架构调整建议 |

> COO角色的核心价值在于提供**企业内部视角**，回答"外部方案在公司内部能否执行得动"这个问题。券商/律师/审计师/税务是"外部专业服务视角"，COO是"内部操盘视角"，两者互补。

### 2.2 交叉审核人选择原则

从专业Agent中选定2名作为交叉审核人。选择标准：

- 专业互补性强（如券商+律师，一个看估值一个看合规）
- 交叉审核人也要产出自己的研究报告（同时是被审核方）

### 2.3 任务分配方式

**主力模式：Task**。用TaskCreate创建任务给Agent——天然隔离、可追踪、产出明确。六个阶段中，Agent的研究、交叉审核、辩论、修改均通过Task模式驱动。

**辅助模式：SendMessage**。仅在需要Agent简单确认或快速沟通时使用，不作为主要工作流驱动方式。

```
需要Agent产出交付物 → TaskCreate（主力）
标准化流程 → Workflow
需求不清晰 → grill-me 深挖
需要Agent简单确认 → SendMessage（辅助）
```

### 2.4 Agent人物设定管理

Agent的人物设定文件（persona，通常位于项目 `agents/` 目录）定义了其核心能力、输出规范和引用格式。在项目生命周期中需管理三个节点：

**项目启动前（审阅+优化）**：

| 检查项 | 内容 |
|:---|:---|
| 现有设定是否覆盖本项目所需专业领域 | 如银行Agent默认侧重债权融资，但本项目需要ECM能力（簿记/基石/绿鞋），需在设定中扩充 |
| 市场/主题特定知识缺口 | 如不同上市地的规则体系差异、行业特有的商业模式差异等，需在设定中补充 |
| 引用规范是否与输出规范一致 | 确保[N]引用体系在设定中已明确 |
| **Agent是否能覆盖本项目涉及的法规体系** | 如涉及域外法律体系（美国税法、PCAOB规则、SEC法规等），检查Agent设定中是否有对应知识。**对不熟悉的法规体系，须在设定中增加反例警示和关键判断依据**（仅列术语表不够），否则Agent可能产生方向性错误 |
| **是否需要新增Agent角色** | 如现有团队无法覆盖项目所需的专业领域（如ESG、数据合规、跨境架构等），由主控新增Agent并创建其人物设定 |

**新增Agent规则**：

主控在项目启动前评估现有团队是否覆盖全部专业领域。如发现缺口，按以下规则新增Agent：

1. **创建人物设定文件**：参照现有Agent设定格式，在 `agents/` 目录下创建新文件（`agents/<角色名>.md`），至少包含角色定位、核心能力、输入输出规范、引用规范四个部分
2. **指派收件箱分组**：将新Agent编入现有分组或新建分组
3. **项目结束后评估留存**：该Agent是否仅本项目需要（临时角色）还是可复用于后续项目（常驻角色）。常驻角色保留设定文件，临时角色归档但标注适用范围

**任务派发时（同步）**：派活前让所有Agent（含新增）读取自己的设定文件，确认理解角色边界后再开始研究。

**项目结束后（沉淀更新）**：
根据项目中暴露的问题更新设定：

| 暴露的问题 | 沉淀到设定的内容 |
|:---|:---|
| Agent跨专业发表了不属于自己领域的判断 | 在设定中明确角色边界和"不做什么" |
| 引用格式在本项目中反复出错 | 强化设定中的引用规范示例 |
| 某领域的专业术语Agent不熟悉 | 在设定中补充术语表和常见法规索引 |
| **域外法规/不熟悉的专业领域出现方向性错误** | 在设定中补充术语表的同时，**附反例警示**（"常见错误写法"——正确术语+错误示例+错误原因）。仅列出正确术语不够，反例更容易触发Agent的警觉 |
| **引用编号管理导致系统性偏移** | 在设定中增加引用编号管理规范："新增引用必须追加到文末，不可在中间插入，否则导致后续编号全部偏移" |
| 与某类Agent协作时频繁越界 | 在设定中标注协作边界和分工矩阵 |

以上三个节点应在方法论六个阶段之前和之后执行，确保Agent设定的持续进化。

## 3. 工作流程（6阶段）

### 阶段1：派活

**主控执行**：
1. 将研究主题拆解为N个子任务（每个对应一个专业Agent）
2. **创建项目文件夹**，含子目录：`研究报告/`、`交叉审核/`

**派活前（权限授权）**：
1. 项目文件夹已创建后，检查其父目录是否存在 `.claude/settings.json` 且已配置 `permissions.allow` 白名单
2. 若不存在：由用户手动执行以下命令创建（Agent不能自改权限配置）：
   ```bash
   mkdir -p "项目目录路径/.claude"
   cat > "项目目录路径/.claude/settings.json" << 'EOF'
   {
     "permissions": {
       "allow": [
         "Edit(/*/项目目录名/**/*.md)",
         "Write(/*/项目目录名/**/*.md)",
         "Bash(mkdir -p /*/项目目录名/**)"
       ]
     }
   }
   EOF
   ```
   替换"项目目录路径"为完整路径、"项目目录名"为最后一级目录名
3. 用户确认已执行后，进入下一步

**派活前（persona审阅）**：
1. 审阅每个Agent的人物设定文件（`agents/`目录），检查其核心能力是否覆盖本项目专业领域
2. 根据项目市场/主题做定向优化
3. 优化后让Agent读取自己的设定，确认角色边界

**主控执行（续）**：
3. 为每个子任务创建Task（TaskCreate），描述明确的研究范围和输出要求。**Task描述中须包含引用规范强制要求**（直接引用7.1模板），避免Agent产出后因缺少[N]引用被退回。**各Agent约定统一的法规引用版本**（如涉及多版本时，在阶段1即确定统一适用的法规文号和修订日期），避免合稿后逐份修复
4. 并行启动所有专业Agent（Agent tool, `run_in_background: true`）

**产物要求**：Agent产出后自主落盘（权限白名单已配置）。若未配置，主控立即代劳写入。

**阶段自查**：
- [ ] 项目文件夹已创建
- [ ] 项目目录 `.claude/settings.json` 权限白名单已配置
- [ ] 所有Agent的人物设定已审阅并优化
- [ ] 所有Task已创建
- [ ] 所有Agent已并行启动
- [ ] 每份Agent产出已落盘到文件夹

### 阶段2：编辑首轮审核

**触发条件**：每份研究报告落盘后**立即**启动编辑审核（不等所有报告完成）。

**编辑审核维度**：
- 格式：标题编号规范、无代码块、表格对齐、仅一个一级标题
- 数据一致性：文中数字前后一致、法规引用准确
- 逻辑：各部分无矛盾、无遗漏
- 引用标注：正文是否有[N]标注，参考文献是否与正文对应
- **同文件内部一致性**：检查同一报告中不同章节对同一事项的描述是否一致（如费用性质、条款引用号码），避免自相矛盾

**输出格式**：
```
✅ 通过项
⚠️ 需修正项（具体位置+建议）
❌ 问题项
📝 总评（100字以内）
```

**阶段自查**：
- [ ] **每份落盘报告立即可见已启动编辑审核**（⚠️ 关键纪律：不得攒到全部产出后再审。主控在收到任一Agent完成通知后，必须**立即**启动编辑审核，不得推迟到其他Agent完成）
- [ ] 编辑审核意见已同步给对应Agent和主控

### 阶段3：交叉审核

**触发条件**：研究报告和编辑首轮审核均完成后启动。

**执行规则**：
1. 交叉审核人审**所有其他Agent**的产出（不含自己的）
2. 交叉审核人从各自专业视角审视，关注：数字一致性、实操性、板块差异、遗漏、矛盾
3. **重要**：交叉审核Agent启动前，被审核文件必须已落盘。若文件仅在对话中，审核Agent无法访问——可在prompt中直接嵌入报告核心内容作为备选方案

**输出格式**：
```
🔗 一致/互补之处
⚠️ 需澄清或补充的地方
💡 从XX专业角度给被审核方的建议
```

**交叉审核意见落盘**：审核完成后，主控将交叉审核意见写入项目 `交叉审核/` 目录，按被审核方命名（如 `交叉审核/legal-counsel-auditor.md` 表示律师对审计师的审核意见）。

**审核意见转交与被审核方确认**：
1. 主控将落盘的交叉审核意见提交给被审核方
2. 被审核方阅读后，对每条⚠️/❌区分处理：
   - **接受**：无异议，进入修改清单
   - **有异议**：需附反驳依据，进入辩论阶段
   - **需澄清**：需补充说明，进入辩论阶段
3. 被审核方输出"交叉审核意见确认书"，列明接受项和有异议项

**阶段自查**：
- [ ] 交叉审核矩阵完整覆盖（每位交叉审核人审了所有其他Agent）
- [ ] 所有交叉审核意见已**落盘**到 `交叉审核/` 目录
- [ ] 被审核方已阅读并确认意见（区分接受/有异议）
- [ ] 有异议项已标记，准备进入辩论

### 阶段4：辩论

**触发条件**：交叉审核全部完成后**必须启动**。此阶段不可跳过。

**核心原则**：主控无权替被指控方认罪。交叉审核意见中的每一条批评——即使是看似明显的事实性错误——被指控方都有权回应。历史上曾出现主控误判"显然是事实错误"跳过了辩论，导致合稿后才发现指控依据有误的教训——跳过辩论直接修改会导致误判。

**前置条件**：阶段3中被审核方标记为"有异议"的项未处理完结的，不得跳过辩论直接修改。

**主控执行**：
1. 收集被审核方在阶段3中标记为"有异议"的争议项
2. 排除纯格式问题（如编号跳跃、引用格式），纳入所有实质分歧
3. **跨报告口径扫描**：提取各报告中涉及"同一事项"的所有数据和表述，对比是否存在不同报告中数据相同但口径/数值不同的情况（如A写"约200家"、B写"约252家"但分别指向暂定名单和总量识别），一并纳入辩论争议清单。此步骤能捕捉交叉审核中未被直接质疑的口径差异
4. 被审核方已确认"接受"的项**不进入辩论**，直接进入修改清单
5. 将争议双方放入同一收件箱，让指控方和被指控方**直接在收件箱对话**

**为什么用收件箱对谈而不用单Agent模拟**：
- 单Agent"同时代表双方"时，事实核查和执行判断混在同一推理过程中，容易弱化被指控方的辩解角度（历史教训：主控误判"显然是事实错误"跳过辩论，结果合稿后才发现指控依据本身有问题）
- 收件箱对谈是真人对辩——指控方亲自重申指控，被指控方亲自回应，对抗性天然存在
- 对辩过程中事实核查自然发生——被指控方会搜索原文来反驳指控，指控方会引用原文来支持主张

**执行规则**：
1. 每项争议的指控方和被指控方在收件箱中直接交流
2. 被指控方有权搜索原文、核对数据来自证清白
3. Agent不回复时，主控介入督促（"请XX就YY指控做出回应"）
4. 分歧无法解决时，按以下路径升级：

```
收件箱对谈 → 达成共识 → 结案
     ↓（无法达成）
双方分歧暴露，全部写入合稿"分歧披露"章节 → 结案
     ↓（某一方沉默不回应）
主控创建Task，强制要求沉默方在指定时限内回应 → 仍不回应 → 记录"未回应"并写入分歧披露
```

**阶段自查**：
- [ ] 被审核方"接受"项已确认（不进入辩论，直接入修改清单）
- [ ] 被审核方"有异议"项已全部纳入辩论
- [ ] 跨报告口径扫描发现的差异已纳入辩论
- [ ] 每项争议的双方已在收件箱直接对话
- [ ] 每场辩论有明确结论（共识/分歧披露/Task强制回应）
- [ ] 沉默争议已被主控发Task督促

### 阶段5：修改 + 编辑逐份终审

**修改规则**：
- 各Agent根据辩论结论和编辑首轮意见修改自己的报告
- 修改按三色分级排序：P0（实质障碍）→ P1（可整改）→ P2（披露即可）→ 格式
- **重要：Agent修改涉及数值计算时，须标注中间步骤，输出前自我验算复核**。跨项目经验表明算术偏差是高频问题
- 每份报告修改完成后，编辑**立即**复核（不等全部改完）

**编辑逐份终审要点**：
- 首轮发现的问题是否已修复
- 辩论结论是否已反映到报告中
- 修改后是否引入新矛盾
- 检查跨报告数据一致性（如费用数据、法规引用等）

**阶段自查**：
- [ ] 每份报告的修正清单已全部处理
- [ ] 每份修正后的报告已通过编辑逐份终审
- [ ] 跨报告矛盾已发现并解决

### 阶段6：合稿 + 编辑合稿复核 + check.sh

**合稿规则**：
- 主控Agent将N份报告整合为一份完整文档
- 合稿保留各专业核心结论，交叉引用详见各专题报告
- 合稿附录列出各专题报告的索引

**编辑合稿复核**：合稿完成后编辑再复核一遍完整文档，检查：
- 跨章节引用是否一致
- 数据在全文中是否自洽
- 各章节风格是否统一

**check.sh校验**：运行引用完整性校验脚本，确保[N]标注规范

**阶段自查**：
- [ ] 合稿已完成
- [ ] 编辑合稿复核已完成
- [ ] check.sh通过（或差异已标注说明）

## 4. 关键机制

### 4.1 交叉审核矩阵

| 审核人 ↓ → 被审核 | 专业A | 专业B | 专业C | ... |
|:---|:---:|:---:|:---:|:---:|
| **交叉审核人1** | — | 审 | 审 | 审 |
| **交叉审核人2** | 审 | — | 审 | 审 |

规则：交叉审核人不审自己。对称矩阵（A审B则B也审A）。

### 4.2 辩论升级路径

```
收件箱对谈 → 达成共识 → 结案，写入修改清单
     ↓（无法达成）
写入合稿"分歧披露"章节 → 结案
     ↓（某一方沉默不回应）
主控创建Task，强制要求回应 → 仍不回应 → 记录"未回应"并写入分歧披露
```

### 4.3 三色分级修正体系

| 级别 | 定义 | 处理方式 | 示例 |
|:---|:---|:---|:---|
| 🔴 P0 | 实质错误，可能误导决策 | 必须立即修正 | 法规数据错误、法律定性错误 |
| 🟡 P1 | 重要缺失或不足，影响方案可用性 | 应尽快修正 | 行业差异化分析缺失、分工矩阵缺失 |
| 🟢 P2 | 优化建议，不影响核心结论 | 可排期修正 | 补充说明、措辞优化 |

### 4.4 编辑三轮闸门

| 轮次 | 时机 | 重点 |
|:---|:---|:---|
| **首轮** | 每份报告产出后立即 | 格式、数据一致性、逻辑 |
| **逐份终审** | 每份报告修改完成后立即 | 首轮问题是否修复、辩论结论是否反映 |
| **合稿复核** | 合稿完成后 | 跨章节一致性、风格统一、check.sh |

每轮独立输出审核报告，不做累积。

### 4.5 check.sh格式校验

引用完整性校验规则：
- 正文中[N]引用的每条，文末参考文献必须有对应条目
- 文末参考文献的每条，正文中必须有对应引用
- [N]编号须从1开始连续，无跳跃
- 参考文献须以`## 参考文献`为章节标题

不同专业领域的引用体系差异（如税务领域的内联法规编号）应在项目启动时约定处理方式。

### 4.6 引用编号管理纪律

Agent在撰写报告中添加引用时，须遵守以下纪律以避免编号偏移：

1. **新增引用必须追加到文末**，不得在现有[N]编号之间插入
2. 如在中间插入引用，须同步重排后续所有编号并运行check.sh验证
3. **每完成一节或整份报告后，立即运行check.sh**验证编号连续性（不要等到全部写完再检查）
4. 正面/反面示例对比：
   - ✅ 正确：写完正文后统一追加到文献列表末尾，按顺序编号
   - ❌ 错误：在正文中间某段新增引用后直接标记[N+1]，未同步重排后文所有编号
5. 多次出现引用编号偏移的项目经验证明：这是跨多个项目反复出现的**系统性通病**，Agent须在写作过程中保持编号管理意识

## 5. 主Agent调度约束

### 5.1 流程纪律

- 主Agent严格按照第3章定义的6阶段顺序执行，**不得跳过、合并或重排阶段**
- 前序阶段的阶段自查全部通过后，方可进入下一阶段
- 主Agent在每阶段开始时检查：该阶段的前置条件是否满足
- 阶段2（编辑首轮）和阶段5（编辑逐份终审）为异步触发机制——每份报告完成即触发，无需等待全部完成

### 5.2 走样检查

主Agent在每个阶段结束时执行走样检查：

| 走样类型 | 表现 | 纠正方式 |
|:---|:---|:---|
| 产出未落盘 | Agent研究完成但报告未写入文件，下一阶段Agent无法读取 | 立即将产出写入项目文件夹 |
| persona未更新 | Agent设定与本项目市场/主题不匹配（如银行Agent无ECM能力却被派去研究簿记建档） | 回退到阶段1派活前，补persona审阅和定向优化 |
| 跳过交叉审核 | 主Agent直接让Agent修改报告，没有经过交叉审核和辩论 | 回退到阶段3，补走交叉审核流程 |
| 修改未经编辑确认 | Agent改完报告后直接合稿，未通过逐份终审 | 回退到阶段5，补编辑逐份终审 |
| 辩论未闭环 | 争议搁置未处理，直接进入了修改阶段 | 回退到阶段4，补辩论或写入分歧披露 |
| **跳过辩论** | 主控自行判断"全是事实性错误无需辩论"，跳过阶段4直接进入修改 | **立即回退到阶段4**。主控无权替被指控方认罪——每一条指控都必须经过双方辩论验证 |
| **辩论争议清单不完整** | 辩论仅涵盖了交叉审核中的直接批评，未纳入跨报告口径差异扫描发现的矛盾（如A写"200家"B写"252家"但各指向不同统计口径），导致合稿阶段仍暴露数据不一致 | 回退到阶段4主控执行步骤3，补做跨报告口径扫描，将口径差异纳入辩论 |
| 合稿未复核 | 主Agent合稿后直接交付，未经过编辑合稿复核和check.sh | 回退到阶段6，补编辑复核和check.sh |
| **编辑审核攒批** | 主控等到全部报告产出后才启动编辑审核，而非每份落盘立即审 | 立即启动编辑逐份审核。已完成的研究报告不因等待其他报告而延迟审核 |
| **法规版本不统一** | 各Agent在报告中引用了同一法规的不同修订版本或不同条款号，合稿后需逐份修正 | 阶段1派活时各Agent约定统一引用版本；编辑审核时增加法规版本一致性检查 |
| **交叉审核意见未落盘** | 交叉审核意见仅在对话中产出，未写入 `交叉审核/` 目录，后续被审核方无法追溯阅读 | 修改规则：交叉审核完成后主控立即将意见写入文件落盘，然后再转交被审核方 |

### 5.3 阶段门禁

每个阶段结束后，主Agent向用户汇报：
1. 当前阶段产物清单（有形产出）
2. 阶段自查结果（全部通过/部分未通过及原因）
3. 是否进入下一阶段

## 6. 防坑清单

| 坑 | 预防措施 |
|:---|:---|
| **Agent产出没落盘** | 阶段1完成后立即Write到项目文件夹；阶段自查检查文件存在 |
| **交叉审核找不到文件** | 阶段3启动前确认被审核文件已落盘；必要时在prompt中嵌入核心内容 |
| **法规版本过时** | 研究任务prompt中要求标注法规文号和生效日期；交叉审核时核验版本 |
| **引用体系不统一** | 项目启动时约定统一引用格式；税务/法律等特殊领域可保留专业格式但需加索引 |
| **数据口径矛盾** | 阶段5编辑逐份终审时专门检查跨报告数据一致性；辩论前增加跨报告口径扫描 |
| **Agent修改权限受限** | 后台Agent写入被拦截 | 根本解：阶段1派活前已授权（用户手动创建白名单）。若遗漏，紧急补救：主控代劳落盘+立即补授权 |
| **审核意见中的误判** | 辩论阶段要求审核方引用原文具体行号作为指控依据 |
| **编辑审核滞后** | 阶段2和阶段5采用异步触发——产出即审，不攒到一起 |
| **跨报告口径差异未进入辩论** | 辩论阶段增加"跨报告口径扫描"——主控提取各报告中涉及同一事项的数据对比，将口径差异纳入争议清单。单份交叉审核不一定发现口径差异，但合稿后暴露 |
| **Agent对域外法规产生方向性错误** | Persona审阅时针对不熟悉的法律体系增加反例警示（如"常见错误：IRD不是美国税法标准术语"）；编辑首轮审核时对不熟悉的法律/税务段落重点核查术语和方向性判断 |
| **法规引用版本不统一** | 阶段1派活时各Agent约定统一引用的法规版本和修订日期；编辑首轮审核时检查各报告引用的法规版本一致性 |
| **Agent算术计算偏差** | 涉及数值计算时，Agent须标注中间步骤便于复核；编辑审核时对关键计算结果做验算 |
| **同文件内部自相矛盾** | 编辑审核增加"同文件内部一致性"维度——检查同一报告中不同章节对同一事项的描述是否一致 |

## 7. 模板

### 7.1 研究任务prompt

```
你是一名[角色名称]。请深入研究[研究主题]，输出一份详尽的研究报告。

研究任务：
1. [子任务1 — 具体范围和要求]
2. [子任务2 — 具体范围和要求]
...

要求：
- 中文输出，格式清晰
- 法规引用需标注完整文号和生效日期
- 数据需标注来源
- **引用格式强制要求**：正文必须用[N]标注引用，文末设## 参考文献列表。**缺少[N]引用可能导致报告退回修改**
- 输出完成后检查check.sh通过
```

### 7.2 交叉审核prompt

```
你是[角色A]（已完成了[领域]的研究）。请从[角色A]视角，交叉审核[角色B]的研究报告。

审核维度：
1. 数字交叉验证：[角色B]的数据、比例与你了解的行业实际是否一致
2. 专业互补性：是否有遗漏的重要事项
3. 实操性评估：建议在实务中是否可行
4. 矛盾发现：与你的研究有无矛盾
5. 协作建议：哪些部分需要与你或其他角色衔接

输出格式：
🔗 一致/互补之处
⚠️ 需澄清或补充的地方
💡 给[角色B]的建议
```

### 7.3 辩论（收件箱对谈）

**发起**：主控将争议双方的⚠️/❌指控发送到共享收件箱。

**指控方回应格式**：
```
@[被指控方] 关于你报告中[具体位置]的[具体问题]：
- 原文引用：[引用被审核报告的原文]
- 我的依据：[提供法规/数据/实务来源]
- 请确认是否接受此指控，或提供反证
```

**被指控方回应格式**：
```
@[指控方] 关于[具体指控]：
- 接受 / 部分接受 / 不接受
- 反证或说明：[提供原文证据、法规版本说明、或解释]
- 如需修正，预计修正内容：[具体方案]
```

**收件箱对话规则**：
- 每轮回应应引用原文具体行号或法规具体条文
- 被指控方有权搜索原文、核对数据来自证清白
- 讨论聚焦于事实和规则，避免价值判断
- 2轮对谈后仍未达成一致→写入分歧披露
- 沉默超过合理时限→主控创建Task强制要求回应

### 7.4 编辑审核清单

```
格式：
[ ] 标题编号规范（## N. / ### N.N，禁止中文编号）
[ ] 仅一个 # 一级标题
[ ] 无代码块（方案文档禁止）
[ ] 表格对齐统一

数据一致性：
[ ] 文中数字前后一致
[ ] 法规引用准确（文号+生效日期）
[ ] 参考文献与正文引用一一对应

逻辑：
[ ] 各部分无矛盾
[ ] 无遗漏重要事项

交叉报告一致性（仅阶段5逐份终审和阶段6合稿复核时适用）：
[ ] 跨报告数据一致
[ ] 法规引用互不矛盾
[ ] 引用格式统一
```

### 7.5 Agent人物设定审阅清单

**项目启动前（审阅+优化）**：
```
[ ] 审阅每个Agent的现有设定，确认核心能力覆盖本项目专业领域
[ ] 检查市场/主题特定知识缺口（如不同上市地的规则体系差异、行业特有知识等）
[ ] 检查Agent角色边界是否明确（"做什么"和"不做什么"）
[ ] 对缺失的能力领域做定向补充
[ ] 让Agent在接收任务前读取更新后的设定
```

**项目结束后（沉淀更新）**：
```
[ ] 回顾项目中Agent跨专业越界的实例，补充角色边界描述
[ ] 回顾引用格式/数据口径在本项目中反复出错的问题，强化设定中的规范示例
[ ] 补充本项目涉及的新法规体系/市场规则到Agent知识索引
[ ] 补充与特定Agent协作的分工边界
```
